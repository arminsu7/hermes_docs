# SIPE 精度对齐指标详解

> 脚本：`/root/repos/dex_lib/sipe-test/debug_onnx_vs_trt.py`
> 用途：对比 GT 模型（通常 FP32 ONNX）与 Pred 模型（如 TRT engine）的输出精度
> 场景：替换 `build_gwc_volume` 为 TRT plugin 后的精度验证基准

---

## 一、对比框架总览

```
GT 模型（通常 FP32 ONNX）          Pred 模型（如 TRT engine）
     ↓ 推理同一批立体图                  ↓ 推理同一批立体图
  每张图得到 N 个检测                每张图得到 M 个检测
  (box/mask/kpt/category/conf/disp)  (box/mask/kpt/category/conf/disp)
          ↓                                ↓
          └────── _match() 框匹配 ──────────┘
                    ↓
            匹配对 [(oi, ti), ...]
                    ↓
    ┌───────────────┼───────────────┐
    ↓               ↓               ↓
 BBox/Mask AP   关键点 OKS/像素误差   视差/深度 EPE
```

核心思路：GT 模型不是「人工标注」，而是「FP32 参考模型的输出」。所以这个对比衡量的是 **TRT 替换/量化后，输出相对 FP32 参考偏了多少**。

---

## 二、检测框匹配（`_match`）

所有后续指标的前提--必须先把 GT 和 Pred 的检测框配对，才能逐对比较。

### 匹配方法：贪心 + 双向覆盖率

```python
def _bbox_dual_overlap(a, b):
    # inter = 两框交集面积
    # return min(inter/area_a, inter/area_b)
```

用 **双向覆盖率的最小值** 做匹配得分，而不是普通 IoU：

```
普通 IoU = inter / (area_a + area_b - inter)

双向覆盖率 = min(inter/area_gt, inter/area_pred)
```

**为什么不用普通 IoU？** 普通 IoU 像是「两个人握手算重合」，大框包小框时 IoU 也能很高。双向覆盖率要求 **两个方向都高**：既要求 GT 的面积大部分被覆盖，也要求 Pred 的面积大部分被覆盖。这样大框包小框时，小框方向覆盖率低，就不会误匹配。

### 阈值 `MATCH_IOU = 0.92`

双向覆盖率 > 0.92 才算匹配成功。这意味着两框面积比不超过 `1/0.92 ≈ 1.09`--**非常严格**，基本要求两个框几乎一模一样大。这么严格是为了：精度对齐时，我们只关心「同一个物体被检测到后，输出有多大偏差」，不想因为框大小差异引入额外的误差。

### 贪心配对过程

所有可能的 (gt, pred) 组合按分数降序排列，从最高分开始贪心配对，已配过的跳过，分数低于 0.92 就停。最终得到匹配对列表 `pairs` + 未匹配的 GT/Pred 列表。

## 三、匹配统计

这是所有指标的前置--先看匹配率，匹配率低了后面指标都没意义。

### 含义

```
GT 模型检测到 N 个物体
Pred 模型检测到 M 个物体
经 _match() 贪心配对后，成功配对了 K 对
```

### 输出

```
ONNX 总检测数 : 245
匹配对数      : 243  (99.2%)
```

- ONNX 总检测数：GT 模型（FP32）在这批图上总共检出多少个物体
- 匹配对数：Pred 模型成功跟 GT 配上对的物体数
- 匹配率 = 匹配对数 / GT 总检测数 × 100%

### 为什么重要

| 情况 | 含义 | 后续指标可信吗 |
|------|------|---------------|
| 匹配率 < 95% | Pred 漏检（GT 有但 Pred 没有）或框偏太多（IoU 不到 0.92） | 后续指标样本不足，不可靠 |
| 匹配率 ~100% | 几乎每个物体都配上了 | 后续指标有意义 |

### 精度对齐时怎么读

| 匹配率 | 含义 |
|--------|------|
| > 99% | Pred 和 GT 检测几乎一致，可以信任后续指标 |
| 95~99% | 有少量漏检或框偏，后续指标基本可用但需注意样本量 |
| < 95% | 漏检严重或框偏大，先排查检测问题再看精度 |

类比：匹配率像是「考试的出勤率」--人都没到齐，谈成绩没意义。

## 四、BBox & Mask AP / Recall

标准目标检测的精度指标，衡量检测框和分割掩码的质量。这块用 mixedai 自带的 `DetectionEvaluator`，算的是标准 COCO 式 AP。

### AP 是什么

AP（Average Precision）= PR 曲线下面积。

```
对每个检测框：
  IoU = 两个框的交集面积 / 并集面积
  如果 IoU > 阈值（如 0.5）-> 算 TP（True Positive，正确检测）
  如果 IoU < 阈值 -> 算 FP（False Positive，误检）

Precision = TP / (TP + FP)  = 检出的有多少是对的
Recall    = TP / (TP + FN)  = 该检的有多少检出来了

PR 曲线：以不同置信度阈值切分，画 Precision vs Recall 曲线
AP = PR 曲线下面积，[0, 1]
```

### 这里怎么用

这里不是「人工标注 vs 模型」，而是「GT 模型输出 vs Pred 模型输出」：

```python
evaluator.update_data_online(pred_insts, gt_insts)
metrics = evaluator.evaluate()
```

### 5 个 IoU 阈值

```python
EVAL_IOUS = (0.5, 0.6, 0.75, 0.8, 0.95)
```

| IoU 阈值 | 含义 | 类比 |
|----------|------|------|
| 0.5 | 两框有 50% 重叠就算匹配 | 及格线 |
| 0.75 | 两框 75% 重叠 | COCO 标准 |
| 0.95 | 两框几乎一模一样 | 严苛线 |

阈值越高，框位置差一点点就匹配不上，AP 就掉。所以高阈值下的 AP 对框位置偏差最敏感。

### 输出

```
[All Classes]  [bbox]
                          @0.5     @0.6     @0.75    @0.8     @0.95
  AP                       1.0000   1.0000   1.0000   0.9959   0.9184
  Recall                   1.0000   1.0000   1.0000   1.0000   1.0000
  TP                       243      243      243      243      243
  FP                       0        0        0        1        19
  GT                       243      243      243      243      243
```

### 每个字段含义

| 字段 | 含义 |
|------|------|
| **AP** | PR 曲线下面积。1.0 = 完美，越低说明 Pred 框跟 GT 框偏差越大 |
| **Recall** | 召回率 = TP / GT 总数。1.0 = 没漏检，低于 1.0 说明漏了 |
| **TP** | True Positive，正确匹配的检测数 |
| **FP** | False Positive，误检数（Pred 有但 GT 没有，或 IoU 不够） |
| **GT** | Ground Truth 总检测数 |

### BBox 和 Mask 的区别

```
BBox metric：用矩形框算 IoU
Mask metric：用实例分割掩码算 IoU（像素级）
```

Mask 比 BBox 更严格--框只要位置对就行，mask 要求物体轮廓也对。

### 精度对齐时怎么读

| AP@0.95 | 含义 |
|----------|------|
| 1.0 | 框几乎完全一致，plugin 无影响 |
| 0.9~1.0 | 有轻微偏差，可能量化引入 |
| < 0.9 | 框位置明显偏了，排查检测链路 |
| Recall < 1.0 | 有漏检，检测置信度可能因量化下降 |

类比：AP@0.95 像是「用游标卡尺量两个零件尺寸是否一致」，0.5 阈值像「用卷尺量大概对不对」。

## 五、关键点 OKS（Object Keypoint Similarity）

OKS 是 COCO 关键点任务的标准指标，衡量两组关键点的相似度。

### 公式

```
OKS = mean( exp( -(dx² + dy²) / (2 * σ² * area) ) )
```

逐项拆：

- `dx² + dy²`：每个关键点的坐标误差平方和（欧氏距离平方）
- `σ`（sigma）：容忍度因子。σ 越小，对误差越敏感
- `area`：bbox 面积，做尺度归一化
- `exp(-...)`：高斯衰减，误差 0 时 OKS=1，误差越大越接近 0

### σ 的作用

```
σ=0.01：area=10000 的物体，误差 1px 时
  e = (1) / (2 * 0.0001 * 10000) = 0.5
  OKS = exp(-0.5) = 0.607

σ=0.10：同样误差 1px
  e = (1) / (2 * 0.01 * 10000) = 0.005
  OKS = exp(-0.005) = 0.995
```

σ 小像是「放大镜」--小误差也扣很多分。σ 大像是「远视眼」--大误差也才扣一点。

### 三种 sigma

| sigma | 严格度 | 用途 |
|-------|--------|------|
| 0.01 | 极严格 | mixedai 原版，对齐 tiny 偏差 |
| 0.05 | 中等 | COCO 标准区间 |
| 0.10 | 宽松 | 看整体趋势 |

### OKS 阈值通过率

```
OKS > 0.5 的匹配对占 95.0%
OKS > 0.9 的匹配对占 82.3%
```

类似 AP 的思路：不同严格度下「有多少比例的匹配对关键点足够一致」。

### 精度对齐时怎么读

| OKS mean (σ=0.01) | 含义 |
|--------------------|------|
| > 0.95 | 关键点几乎无偏差 |
| 0.8~0.95 | 有轻微偏差 |
| < 0.8 | 明显偏差，排查关键点链路 |
| σ=0.01 低但 σ=0.10 高 | 有小误差但整体趋势对 |

类比：OKS 像是「体操打分」--σ 小是严苛裁判（手指轻微抖动都扣分），σ 大是宽松裁判（大方向对就给高分）。

## 六、关键点像素误差

OKS 经过面积归一化，不直观。脚本额外算了**原始像素误差**，最直观。

### 含义

同一个物体上同一个关键点，GT 模型和 Pred 模型预测出来的坐标，在 x 方向（水平）和 y 方向（垂直）各偏了多少像素。

```
GT 模型（FP32）预测:   x=320.5, y=240.1
Pred 模型（TRT）预测:  x=321.8, y=239.5

dx = 321.8 - 320.5 = +1.3 px  (水平偏了 1.3 像素)
dy = 239.5 - 240.1 = -0.6 px  (垂直偏了 0.6 像素)
```

脚本里取的是**绝对值**：

```python
all_dx.append(abs(kpt_trt[vis2, 0] - kpt_onnx[vis2, 0]).mean())
all_dy.append(abs(kpt_trt[vis2, 1] - kpt_onnx[vis2, 1]).mean())
```

所以 dx/dy 永远是正数，表示「偏了多少」，不表示方向。

### 为什么分 dx 和 dy

因为水平方向和垂直方向的偏差来源不同：

**dx（水平方向偏差）** --跟视差（disparity）强相关。

立体匹配的核心是：同一个点在左图和右图中的**水平位移**就是视差。视差算错了，关键点的 x 坐标就会偏。这正是 `build_gwc_volume` 影响的路径：

```
build_gwc_volume 算的是 cost volume
  -> 视差回归 -> 视差图
    -> 视差传给 MixedOne -> 关键点 x 坐标
```

所以如果 `build_gwc_volume` 的 plugin 实现有偏差，**dx 会比 dy 先反映出来**，而且 dx 的偏差量跟视差 EPE 有相关性。

**dy（垂直方向偏差）** --跟视差关系小，主要来自检测网络本身（backbone 特征、解码器等）。如果只有 dx 偏而 dy 正常，基本锁定是立体匹配那条链路的问题。

### 只算双侧可见的关键点

```python
vis2 = (kpt_onnx[:, 2] > 0) & (kpt_trt[:, 2] > 0)
```

只取两个模型**都认为可见**的关键点。因为如果某个关键点在一侧不可见（visibility=0），它的坐标是假的/随机的，拿来比误差没意义。

### 统计方式

每个匹配对（一个物体）算一个 dx 和 dy：

```
物体1: 10个可见关键点 -> 取这10个点 |x差| 的均值 = dx_1
物体2: 8个可见关键点  -> 取这8个点 |x差| 的均值 = dx_2
...
```

然后所有匹配对的 dx 汇总统计：

```
dx_arr = [dx_1, dx_2, dx_3, ...]

mean   = 0.32   # 平均每物体水平偏 0.32 像素
median = 0.21   # 一半物体偏 <0.21 像素
max    = 2.15   # 最差的一个物体偏了 2.15 像素
std    = 0.45   # 偏差波动大不大
```

### 精度对齐时怎么读

| dx mean | 含义 |
|---------|------|
| < 0.5px | 几乎无偏差，plugin 数值等价 |
| 0.5~1px | 有轻微偏差，可能是 fp16/量化引入 |
| > 1px | 明显偏差，build_gwc_volume plugin 可能有问题 |
| > 5px | 严重偏差，plugin 实现肯定有 bug |

dy 一般比 dx 小且稳定（不受视差影响）。如果 dx 偏大但 dy 正常，重点排查 `build_gwc_volume` -> disparity -> keypoint 这条链路。

### 欧氏距离

```
欧氏距离 = sqrt(dx² + dy²)
```

就是勾股定理--dx 和 dy 合成的总位移距离。比单独看 dx/dy 更直观地表示「这个点偏了多远」。

## 七、视差 EPE / D1

这是立体匹配任务的核心精度指标。

### EPE（End-Point Error）

```
EPE = |gt_disp - pred_disp|  (像素)
```

逐像素算视差绝对差。

只在 **GT mask 区域内、双侧视差都 >0** 的有效像素上算：

```python
mask_bool = omask > 0.5        # 只看物体 mask 内
valid = (onnx_d > 0) & (trt_d > 0)  # 双侧有效
```

为什么只在 mask 内：背景区域的视差没意义（不是物体），而且背景视差可能有大面积噪声，拉偏统计。

### D1 指标

```
D1 >3px (%) = 误差超过 3 像素的像素占比
D1 >1px (%) = 误差超过 1 像素的像素占比
```

D1 是「坏点率」--误差超过阈值的像素百分比。

### 累计分布

```
EPE ≤ 0.5px : 98.2%  (12345/12567 px)
EPE ≤ 1.0px : 99.5%  (12504/12567 px)
EPE ≤ 2.0px : 99.9%  (12555/12567 px)
EPE ≤ 3.0px : 100.0% (12567/12567 px)
EPE ≤ 5.0px : 100.0%
```

展示误差分布的「尾巴」：多少比例的像素误差在阈值以内。

### 统计量

```
  视差 EPE (px)   mean=0.032  median=0.001  min=0.000  max=2.150  std=0.123
```

| 统计量 | 含义 |
|--------|------|
| mean | 平均误差，整体水平 |
| median | 中位数，比 mean 抗异常值 |
| min | 最小误差（应有 0.000） |
| max | 最大误差，看有没有极端坏点 |
| std | 标准差，误差波动大不大 |

### 精度对齐时怎么读

| EPE mean | 含义 |
|----------|------|
| < 0.1px | 视差几乎无偏差，plugin 数值等价 |
| 0.1~1px | 有轻微偏差，可能量化引入 |
| > 1px | 明显偏差，build_gwc_volume plugin 可能有问题 |
| max > 5px | 个别像素严重偏，边缘 case |

类比：EPE mean 像是「体温计」--plugin 如果有问题，视差链路会先发烧。D1 像是「X 光」--看出有多少像素「生病」了。

## 八、深度 EPE

跟视差 EPE 完全一样的逻辑，只是单位从像素变成了米。

### 视差怎么转深度

```
depth = baseline * fx / disparity
```

需要相机参数：
- `fx`：焦距（像素单位）
- `baseline`：双目基线长度（米）

如果没传相机参数，depth 这块会输出「无（未提供相机参数）」。

### 跟视差 EPE 的关系

深度误差不是视差误差的线性放大。因为 `depth = k / disp`：

```
disp=10px 时，depth=15m  ->  disp 偏 1px 变成 9px，depth=16.7m，深度偏了 1.7m
disp=50px 时，depth=3m   ->  disp 偏 1px 变成 49px，depth=3.06m，深度偏了 0.06m
```

视差小（远距离物体）时，同样 1px 视差误差，深度误差被放大很多。所以深度 EPE 对远距离物体更敏感。

### 精度对齐时怎么读

| depth EPE mean | 含义 |
|----------------|------|
| < 0.001m (<1mm) | 深度几乎无偏差 |
| 0.001~0.01m | 有轻微偏差 |
| > 0.01m (>1cm) | 明显偏差 |

## 九、总结：各项指标对 build_gwc_volume plugin 的敏感度

| 指标 | 敏感度 | 原因 |
|------|--------|------|
| 视差 EPE | ★★★★★ | build_gwc_volume 直接算 cost volume -> 视差，最直接 |
| 关键点 dx | ★★★★ | 视差偏差传到关键点 x 坐标 |
| 深度 EPE | ★★★★ | 视差 EPE 的非线性放大，远距离更敏感 |
| BBox AP@0.95 | ★★★ | 框位置间接受视差影响 |
| 关键点 dy | ★★ | 垂直方向不受视差影响，主要看检测网络 |
| 匹配率 | ★ | 只有严重偏差才影响匹配 |

排查 plugin 问题时，**先看视差 EPE**--如果它接近 0，其他指标基本都不会有问题。如果视差 EPE 偏大，再顺着链路看 dx、BBox AP。

## 十、脚本用法

```bash
python debug_onnx_vs_trt.py \
    --gt    sources/model_fp32.onnx \
    --pred  sources/model_int8.engine \
    --image-dir       datas/test/rgb/ \
    --right-image-dir datas/test/rightrgb/ \
    --fx 3174.33 --baseline 0.1465 --cx 990.0 --cy 544.3
```

### 参数说明

| 参数 | 说明 |
|------|------|
| `--gt` | GT（参考）模型路径，`.onnx`（ort）或 `.engine/.trt/.plan`（trt），后端自动识别 |
| `--pred` | Pred 模型路径，同上 |
| `--image-dir` | 左图目录 |
| `--right-image-dir` | 右图目录（按排序后与左图一一配对） |
| `--fx` | 相机焦距 fx（像素），用于深度计算 |
| `--fy` | 相机焦距 fy（像素），默认等于 fx |
| `--cx` | 主点 cx（像素） |
| `--cy` | 主点 cy（像素） |
| `--baseline` | 双目基线长度（米） |
| `--model-input-size` | SIPE 模型输入尺寸（默认 512，需与导出时一致） |

### 后端自动识别

- `.onnx` -> ONNX Runtime（ort）
- `.engine/.trt/.plan` -> TensorRT（trt）
- `--gt` 和 `--pred` 可以是任意组合（ONNX vs ONNX、ONNX vs TRT、TRT vs TRT）
